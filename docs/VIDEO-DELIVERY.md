# Video delivery

How the videos actually reach a visitor, what is wrong with that today, and the
two fixes — one of which takes a single command.

## Where things stand

Measured against the live bucket (`npm run check-media`, plus `ffprobe` over the
public URLs):

| | |
|---|---|
| Videos | 28 |
| Total running time | 128 minutes |
| Total bytes | **7.75 GB** |
| Mean bitrate | **8.6 Mbps** |
| Worst offender | *One of Us* — 736 MB, 19.6 Mbps |
| Source resolutions | 13 × 1080p, 10 × 720p, 5 × 540p |
| Renditions per video | 1 (the export itself) |
| `Cache-Control` | `private, max-age=0` on every object |

Two separate problems live in that table.

**There is only one rendition.** A visitor on hotel wifi or a phone gets the
same 8–20 Mbps file as someone on fibre. There is no lower rung to fall back
to, so playback stalls rather than degrading. 19.6 Mbps is an editing master,
not a delivery format.

**Nothing is cacheable.** Firebase Storage defaults to `private, max-age=0`
when an object is uploaded without `Cache-Control`. Browsers and CDNs both
honour that, so every play and every grid render re-downloads from the origin
in full. Rewatching a video costs the same bandwidth as the first watch, and
the thumbnails alone are re-fetched on every page view.

## Fix 1: set Cache-Control (one command, no re-encode)

This is the cheapest win available and it changes nothing about the files.

```bash
gcloud storage objects update \
  "gs://laundromat-zat.firebasestorage.app/videos/**" \
  "gs://laundromat-zat.firebasestorage.app/thumbnails/**" \
  --cache-control="public, max-age=31536000, immutable"
```

`immutable` is safe here because objects are never edited in place — a changed
video is uploaded under a new name with a new download token, which is a new
URL. Re-run `npm run check-media` afterwards; the "served uncacheable" warning
should disappear.

Do this whether or not you go on to Fix 2. New uploads need the same treatment,
so pass `--cache-control` when you upload rather than fixing it after the fact.

## Fix 2: adaptive bitrate (HLS)

The player already supports it. `src/hooks/useAdaptiveVideoSource.ts` prefers a
video's `streamUrl` when it has one, and:

- plays the HLS playlist natively on Safari and iOS, with no JavaScript library
  involved at all;
- loads `hls.js` on demand elsewhere — it is a separate chunk, never in the
  main bundle and deliberately kept out of the service worker precache, so a
  visitor who does not open an HLS video never downloads it;
- falls back to the progressive file if HLS fails for any reason.

A video without a `streamUrl` keeps playing exactly as it does now, so this can
be rolled out one video at a time.

### Transcoding

```bash
npm run transcode-hls -- ~/Movies/one-of-us.mov
```

Needs `ffmpeg` locally (`brew install ffmpeg`). It probes the source, picks the
ladder rungs the source can fill without upscaling, and writes
`hls-out/<slug>/` plus an `upload.sh` for it.

Measured on the first 60 seconds of *One of Us* (18.9 Mbps source):

| Rung | Bitrate | vs. source |
|---|---|---|
| 1080p | 5.5 Mbps | 3.5× smaller |
| 720p | 2.9 Mbps | 6.6× smaller |
| 480p | 1.5 Mbps | 12.8× smaller |
| 360p | 0.9 Mbps | 20.3× smaller |

The whole four-rung ladder is 77 MB against the source's 135 MB, so this
*reduces* storage as well as delivery. Encoding cost about two minutes of CPU
per minute of 1080p video.

### Why the output looks the way it does

Firebase Storage issues one download token per object, and a normal HLS encode
produces hundreds of numbered segments — hundreds of tokens to bake into the
playlists. So each rung is encoded as fMP4 with `-hls_flags single_file`: one
media object that the playlist seeks into with byte ranges, with the init
segment carried inside it. A four-rung ladder is nine objects in total (four
playlists, four media files, one master), each with one token.

The tokens are generated by the script rather than read back after upload,
because a Firebase download token is just the object metadata key
`firebaseStorageDownloadTokens`. Setting it at upload time makes every URL
predictable, so the playlists can be written with their final absolute URLs
before anything is uploaded.

### Publishing

`hls-out/<slug>/upload.sh` is generated but never run for you — it needs
credentials for the bucket. Read it, then run it. It sets the download token
and the long `Cache-Control` on every object, and prints the `streamUrl` to add
to the video's entry in `src/data/projects.json`.

Transcoding deliberately does not print that URL. The token is decided before
the upload, so a URL shown next to "done" reads as a finished result and is
easy to paste into `projects.json` while the objects are still only on your
laptop. Only `upload.sh` prints it, and only once every object is in the
bucket:

```json
{
  "title": "One of Us",
  "projectUrl": "https://firebasestorage.googleapis.com/.../videos%2Fone-of-us.m4v?alt=media&token=...",
  "streamUrl": "https://firebasestorage.googleapis.com/.../streams%2Fone-of-us%2Fmaster.m3u8?alt=media&token=..."
}
```

Keep `projectUrl`. It is the fallback source, and it is what `og:video` points
at for link unfurlers, which do not speak HLS.

Then check it: `npm run check-media` follows a `streamUrl` into its variant
playlists and the media they reference, so a half-finished upload — master
loads, renditions do not — shows up as a failure rather than as a video that
quietly falls back to the full-size file.

### CORS: the thing that makes a stream silently pointless

A progressive `<video src>` needs no CORS — the browser's media pipeline
fetches it directly. **hls.js does not have that luxury**: it pulls the
playlists and segments over XHR, so the browser enforces CORS on every one of
them. A stream whose responses carry no `Access-Control-Allow-Origin` still
plays in Safari and on iOS, which use native HLS and never touch XHR, and
fails in every other browser — where the player falls back to the full-size
file. Playback keeps working, so the failure is invisible unless you look for
it. `npm run check-media` looks for it.

Firebase's download endpoint answers the *preflight* with
`Access-Control-Allow-Origin: *` but, as shipped, sends no such header on the
actual GET, which is the one the browser checks. Set a CORS policy on the
bucket:

```bash
cat > /tmp/cors.json <<'JSON'
[
  {
    "origin": ["https://laundromatzat.com"],
    "method": ["GET", "HEAD"],
    "responseHeader": [
      "Content-Type", "Content-Length", "Content-Range", "Accept-Ranges", "Range"
    ],
    "maxAgeSeconds": 3600
  }
]
JSON

gcloud storage buckets update gs://laundromat-zat.firebasestorage.app \
  --cors-file=/tmp/cors.json
```

Then confirm, rather than assuming — a bucket CORS policy is documented for
the `storage.googleapis.com` APIs, and whether it reaches the
`firebasestorage.googleapis.com` download frontend is worth proving on your
own bucket:

```bash
curl -sS -o /dev/null -D - -H "Origin: https://laundromatzat.com" \
  "<the streamUrl>" | grep -i access-control-allow-origin
```

A line back means it works. Nothing back means the policy does not reach that
frontend, and the stream has to be served from `storage.googleapis.com`
instead — which needs the `streams/` objects made publicly readable (they are
already public in effect, via their tokens) and that host added to both
`connect-src` and `media-src` in the CSP in `index.html`.

Do not add a `streamUrl` to `projects.json` until this passes. Until it does,
adding one makes things slightly worse everywhere but Safari: hls.js is
downloaded, fails, and the full-size file is fetched anyway.

### When a stream URL returns 403

Firebase answers `403 Permission denied` both for an object that does not
exist and for one whose download token does not match, so the status alone
cannot tell you which. Ask the bucket:

```bash
gcloud storage ls -L gs://laundromat-zat.firebasestorage.app/streams/<slug>/
```

- **Nothing listed** — `upload.sh` has not run, or exited partway.
- **Objects listed, but no `firebaseStorageDownloadTokens` under Metadata** —
  the upload dropped the custom metadata. Re-run `upload.sh`.
- **The token listed differs from the one in the playlist URLs** — the object
  was uploaded more than once and Firebase minted a fresh token. Re-run
  `transcode-hls` so the playlists and the metadata are generated together.

## If you would rather not self-host

`streamUrl` is just an HLS URL, so a managed host works without any code
change — Cloudflare Stream, Mux and Bunny Stream all hand back an `.m3u8`.
The trade-off is a per-minute bill against the transcoding and upload work
above, and one extra origin to add to `media-src` and `connect-src` in the CSP
in `index.html`.

Worth knowing if YouTube or Vimeo comes up instead: home footage cut to
commercial music routinely picks up Content ID claims, which can mute or
region-block a video. A dedicated video host avoids that.

## Content Security Policy

Adaptive playback needs three things the CSP in `index.html` already grants:

- `connect-src` for the media host — hls.js fetches playlists and segments over
  XHR, not through the `<video>` element;
- `blob:` in `media-src`, because MSE feeds the element from a blob URL;
- `worker-src 'self' blob:`, because hls.js runs its demuxer in a blob-backed
  worker. Without it hls.js still works, but on the main thread.

Any new media host has to be added to `connect-src` **and** `media-src`.
